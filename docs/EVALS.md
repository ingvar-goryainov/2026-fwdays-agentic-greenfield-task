# EVALS.md — agents-lint

> Verification strategy for the project. Defines how we know the tool works
> correctly, how we evaluate agent-generated code quality, and the checklist
> a human reviewer uses before marking a capability as done.

## 1. Tool evals (does agents-lint work correctly?)

### 1.1 Rule correctness evals

Each rule has fixture-based evals. A rule is correct when it:
- ✅ Returns zero findings for every file in `testdata/<rule_id>/valid/`
- ✅ Returns at least one finding for every file in `testdata/<rule_id>/invalid/`
- ✅ Reports the correct severity (error vs warning) per config
- ✅ Reports accurate file path and line number in findings

| Rule | Valid fixtures (min) | Invalid fixtures (min) | Edge cases to cover |
|------|---------------------|----------------------|---------------------|
| S001 | 1 (file exists) | 1 (file missing) | Empty directory, nested path |
| S002 | 2 (minimal sections, full sections) | 2 (missing section, wrong heading level) | H2 vs H3 confusion, extra sections OK |
| S003 | 2 (complete block, multiple agents) | 2 (missing role, missing name) | Agent with only tools, agent with only context |
| S004 | 1 (unique names) | 2 (exact duplicate, case-insensitive dup) | Unicode names, whitespace in names |
| S005 | 2 (valid YAML, no frontmatter at all) | 2 (invalid YAML, unclosed delimiters) | Empty frontmatter `---\n---`, nested objects |
| C001 | 1 (all paths resolve) | 2 (missing file, missing directory) | Relative vs absolute, `../` paths, glob patterns |
| C002 | 1 (tool has evidence) | 1 (tool referenced, no evidence) | Multiple tools, partial evidence |

### 1.2 Output quality evals

| Eval | Method | Pass criterion |
|------|--------|---------------|
| Actionable messages (BC-OUTPUT-02) | Golden file comparison | Each finding message contains: what's wrong + what to do |
| Text format (FR-OUT-01) | Golden file: `testdata/reporter/golden/` | Exact match with expected terminal output |
| Summary line (FR-OUT-02) | Assertion in test | Format: `N error(s), M warning(s)` |
| Success line (FR-OUT-04) | Assertion in test | Format: `✓ AGENTS.md is valid (N rules passed)` |
| NO_COLOR respected (BC-OUTPUT-01) | Test with env var set | No ANSI escape codes in output |

### 1.3 Integration evals

| Eval | Method | Pass criterion |
|------|--------|---------------|
| Clean scan on valid repo | `agents-lint scan testdata/integration/valid-repo/` | Exit 0, success message |
| Failing scan on broken repo | `agents-lint scan testdata/integration/broken-repo/` | Exit 1, expected findings |
| Init produces valid file | `agents-lint init` → `agents-lint scan .` | Exit 0 on the generated file |
| Config override works | `--config custom.yaml` disables a rule | Disabled rule not reported |
| SARIF output valid | `--format sarif` output → validate against SARIF schema | Schema-valid JSON |

### 1.4 Performance evals

| Eval | Method | Pass criterion |
|------|--------|---------------|
| Scan speed (NFR-PERF-01) | `go test -bench BenchmarkScan` with 500-line AGENTS.md | < 100ms p95 |
| Binary size (NFR-PERF-02) | `ls -la` after `go build` (stripped) | ≤ 15 MB |
| Build time (NFR-DX-01) | `time go build ./cmd/agents-lint` on clean checkout | < 10s |

### 1.5 Regression evals

- **Method:** Full test suite (`go test ./...`) runs on every commit
- **Pass criterion:** Zero test failures, zero lint warnings
- **Automation:** CI runs tests + linter on every push / PR

## 2. Agent-work evals (did the coding agent produce good code?)

These evals assess the quality of code generated by the `implementer` agent.
The `reviewer` agent (or human) applies them after each capability.

### 2.1 Structural correctness

| Check | How to verify | Fail signal |
|-------|---------------|-------------|
| Matches requirement | Compare implementation against FR-XXXX in requirements.md | Behavior diverges from spec |
| Follows architecture | Rule code lives in `internal/rules/`, no cross-package imports that break layering | Import from `cmd/` in `internal/`, or `reporter` imported by `rules` |
| Library-first | No `fmt.Print`, `os.Exit`, or `log.Fatal` in `internal/` | Direct stdout/stderr writes in library code |
| No globals | No `var` at package level that holds mutable state | Package-level mutable variable |
| Error handling | Errors wrapped with context, never panics | Bare `panic()`, unwrapped errors |

### 2.2 Test quality

| Check | How to verify | Fail signal |
|-------|---------------|-------------|
| Table-driven | Tests use `[]struct{name, input, want}` pattern | Single-case tests or repeated logic |
| Fixtures used | Tests read from `testdata/`, not inline strings > 5 lines | Large inline markdown strings in test files |
| Edge cases present | At least one "tricky" case per rule (see 1.1 table) | Only happy-path tests |
| Coverage | `go test -cover` on the rule file | < 90% line coverage |
| Race-safe | `go test -race` passes | Race condition detected |

### 2.3 Code quality

| Check | How to verify | Fail signal |
|-------|---------------|-------------|
| gofmt clean | `gofmt -d .` produces no diff | Formatting differences |
| golangci-lint clean | `golangci-lint run` exits 0 | Lint warnings/errors |
| Naming conventions | Types PascalCase, files lowercase, rule files `<id>.go` | Inconsistent naming |
| No dead code | No unused functions, variables, imports | `deadcode` or lint warning |
| Commit message | Proper prefix + requirement ID | Missing prefix or ID |

### 2.4 Agent behavior red flags

Watch for these patterns — they indicate the agent is "vibecoding":

| Red flag | What it looks like | Correct response |
|----------|-------------------|-----------------|
| Skipped tests | "Implementation complete" without running `go test` | Reject — run the tests |
| Hallucinated API | Using a goldmark/cobra function that doesn't exist | Reject — verify against docs |
| Over-engineering | Adding features not in requirements (scoring, plugins) | Reject — scope creep |
| Copy-paste errors | Same bug in multiple rule files | Flag — did agent actually test each? |
| Optimistic "works" | "This should work" without evidence | Reject — show the green test output |

## 3. Human reviewer checklist

Apply this checklist before marking an OpenSpec capability as `apply`-complete.

### Per-capability sign-off

```markdown
## Reviewer checklist — [capability-slug]

### Spec conformance
- [ ] Every FR-* requirement listed in the capability plan is implemented
- [ ] Behavior matches the requirement description exactly (not "close enough")
- [ ] No extra features added beyond what's specified

### Code quality
- [ ] `go test ./...` passes (run it yourself, don't trust agent output)
- [ ] `golangci-lint run` is clean
- [ ] Coverage ≥ 90% on new `internal/` files
- [ ] No `fmt.Print` / `os.Exit` in library code
- [ ] Error messages are actionable (what's wrong + how to fix)

### Architecture
- [ ] New code is in the correct package per AGENTS.md structure
- [ ] No circular imports
- [ ] Types/interfaces defined in `internal/types/` (not inline)
- [ ] Rule follows the `Check(doc, cfg) []Finding` signature

### Testing
- [ ] Fixtures exist: ≥2 valid, ≥2 invalid per rule
- [ ] Tests are table-driven
- [ ] Edge cases from EVALS.md section 1.1 are covered
- [ ] Golden files updated if output format changed

### Process
- [ ] Commits reference requirement IDs
- [ ] OpenSpec tasks.md is complete (all tasks checked off)
- [ ] No dependency on unfinished capabilities
- [ ] AGENTS.md still validates against itself (dogfooding)
```

### Final MVP sign-off (before PR submission)

```markdown
## MVP sign-off checklist

### Completeness
- [ ] All accepted-status requirements are implemented
- [ ] `agents-lint scan .` works on this repo (dogfooding)
- [ ] `agents-lint init` generates a file that passes `scan`
- [ ] README has: installation, usage, rule catalog, config reference

### Verification
- [ ] Full test suite green: `go test ./...`
- [ ] Linter clean: `golangci-lint run`
- [ ] Integration tests pass (valid-repo + broken-repo)
- [ ] Performance benchmark within limits

### Demo readiness
- [ ] 1-2 min video recorded showing the tool in action
- [ ] PR description documents agentic practices applied
- [ ] Human vs agent responsibilities clearly stated in PR
- [ ] Tools/MCP used are listed in PR description
```

|------|-------------|-----|
| After every rule implementation | Rule fixtures + coverage check | Tester agent |
| After every capability | Full test suite + reviewer checklist | Reviewer agent + human |
| Before PR submission | MVP sign-off checklist + integration evals + benchmark | Human |
| In CI (every push) | `go test ./...` + `golangci-lint run` | Automated |
